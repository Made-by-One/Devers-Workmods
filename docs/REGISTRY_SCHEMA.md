# Registry schema (v2)

`registry.json` is the shared catalog. It is written **only** by
`.github/workflows/update_registry.yml` → `.github/scripts/update_registry.py`.
Clients read it from `raw.githubusercontent.com`, so changes are visible without
a release.

## Document

```json
{
  "schema_version": 2,
  "updated_at": "2026-11-09T12:00:00+00:00",
  "games": [
    { "id": "space-rangers", "name": "Space Rangers", "sdk": "unity" }
  ],
  "mods": [
    {
      "id": "a1b2c3d4",
      "game_id": "space-rangers",
      "name": "Neon UI",
      "version": "1.2.0",
      "author": "your-handle",
      "description": "Neon HUD replacement.",
      "repo": "you/workmods-neon-ui",
      "download_url": "https://github.com/you/workmods-neon-ui/releases/download/v1.2.0/a1b2c3d4.zip",
      "sha256": "9f2c…",
      "icon_url": "https://raw.githubusercontent.com/you/workmods-neon-ui/main/icon.png",
      "banner_url": "",
      "entry_asset": "NeonHud",
      "tags": ["ui", "hud"],
      "updated_at": "2026-11-09T12:00:00+00:00"
    }
  ]
}
```

### Top level

| Field | Type | Notes |
|---|---|---|
| `schema_version` | int | `2`. Readers accept `1` too. |
| `updated_at` | ISO-8601 UTC | Set by the bot on every successful update. |
| `games` | array | Optional catalogue of known games; clients also derive games from mods. |
| `mods` | array | Sorted by `(game_id, name, id)` by the bot. |

### Game

| Field | Type | Notes |
|---|---|---|
| `id` | string | `[a-z0-9._-]`, lower-case. Used as a folder name and SDK parameter. |
| `name` | string | Display name. |
| `sdk` | string | `unity` for now; reserved for future engines. |

Games with an id but no profile in the client are still selectable in filters.

### Mod

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Stable mod id. Generated by the client (8 hex chars); never change it on update. |
| `game_id` | yes | Target game; missing/empty becomes `default`. |
| `name` | yes | Display name. |
| `version` | yes | Free-form but no spaces/slashes; used as the release tag `v<version>`. |
| `author` | no | Free text. |
| `description` | no | Plain text, shown in the detail pane. |
| `repo` | no | `owner/repo` that hosts the release. |
| `download_url` | yes | Direct release asset URL. The client refuses mods without it. |
| `sha256` | no | Hex digest of the ZIP; verified after download when present. |
| `icon_url`, `banner_url` | no | Fetched by the client; failures are silent. |
| `entry_asset` | no | Default asset name for `WorkmodsSDK.LoadAssetBundle`. |
| `tags` | no | Array of strings, searchable. |
| `updated_at` | no | Set by the bot when the entry is written. |

The client ignores unknown fields (`Mod.from_dict` whitelists), so the registry
can gain fields without breaking older clients.

## Version 1 compatibility

Before v1.0 the registry was just `{ "mods": [ … ] }` and mods had no `game_id`.
Readers handle this:

- missing `schema_version` → `1`;
- missing `game_id` → `default`;
- the client shows those entries under the `default` ("Unassigned") profile and
  under **All games**;
- the bot rewrites the file as v2 on its next run.

## Dispatch contract

The client sends `repository_dispatch` to the registry repository:

```http
POST /repos/Made-by-One/Devers-Workmods/dispatches
{
  "event_type": "add_mod",            // or "remove_mod"
  "client_payload": {
    "secret": "<shared secret>",
    "id": "a1b2c3d4",
    "game_id": "space-rangers",
    "name": "Neon UI",
    "version": "1.2.0",
    "author": "your-handle",
    "description": "…",
    "repo": "you/workmods-neon-ui",
    "download_url": "https://github.com/…/a1b2c3d4.zip",
    "sha256": "…",
    "entry_asset": "NeonHud",
    "tags": ["ui"],
    "icon_url": "…",
    "banner_url": "…"
  }
}
```

`remove_mod` only needs `{ "secret", "id" }`.

The Action (`update_registry.yml`):

1. checks out the repository and installs Python 3.12 (no third-party deps);
2. runs `update_registry.py`, which compares the secret with `hmac.compare_digest`
   against the `BOT_SECRET_TOKEN` repository secret — a wrong or missing secret
   fails the job;
3. whitelists known fields (dropping `secret`), normalises `game_id`, coerces
   `tags`, timestamps the entry;
4. replaces the entry by `id`, sorts the list, writes schema v2;
5. validates the JSON, commits and pushes only when something changed.

Concurrency is serialised with `concurrency.group: registry-update`, so two
publishers finishing at once cannot lose an entry.

## Rules the bot enforces

- Unknown events (`delete_everything`) → job fails, registry untouched.
- `add_mod` without `id` → job fails.
- `remove_mod` for an unknown id → succeeds as a no-op.
- The shared secret never appears in `registry.json` (tested).
- Re-publishing the same `id` replaces the previous entry (update semantics).

## Consistency notes

- `download_url` points at the release tag, not at `main`, so old versions remain
  downloadable and the SHA-256 stays valid.
- Icon/banner URLs point at the repository's **default branch** (queried during
  publish), so a repository using `master` still works.
- The registry has no delete history: removing a mod only removes its entry.
